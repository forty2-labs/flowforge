## What this is

Flowforge is a schema-driven CMS and experience platform. Only phase 1 (accounts, workspaces, members, invitations, role guard) is built; phase 2 (content types, generated editor, entries, media) is next. [docs/overview.md](docs/overview.md) has the product model and the phase plan, and [docs/decisions.md](docs/decisions.md) records why each significant choice was made. Add new decisions there with their reason and cost.

## Commands

npm workspaces plus Turborepo, Node 22 or newer. Run from the repository root.

```sh
npm run db:up                          # Postgres and Redis in Docker
npm run db:deploy -w @flowforge/api    # apply existing migrations
npm run dev                            # types watcher, API on :4000, web on :3000

npm run lint
npm run typecheck
npm run test                           # unit tests (only the API has any)
npm run test:e2e -w @flowforge/api     # needs Postgres running
npm run test:visual -w @flowforge/web  # screenshots and accessibility checks; needs Postgres running
npm run build
```

Single tests (Vitest, in the API):

```sh
npm run test -w @flowforge/api -- src/auth/password.spec.ts
npm run test -w @flowforge/api -- -t "name of the test"
npm run test:e2e -w @flowforge/api -- -t "name of the test"
```

After editing `apps/api/prisma/schema.prisma`:

```sh
npm run db:migrate -w @flowforge/api   # creates and applies a migration; commit the file
```

CI runs lint, typecheck, test, test:e2e and build, in that order.

## Architecture

| Package | Job | Depends on |
| --- | --- | --- |
| `packages/types` | Roles, the capability matrix, API response shapes | nothing |
| `packages/ui` | Ink & Signal design tokens and base components | nothing |
| `apps/api` | NestJS REST API. The only code that touches the database. | types |
| `apps/web` | Next.js app. Everything the browser sees. | types, ui |

The two apps never import each other. They share only the two packages and talk over HTTP.

### Request path

The browser talks only to Next.js, never to the API.

1. A server component or server action calls `api()` in [apps/web/src/lib/api.ts](apps/web/src/lib/api.ts), which forwards the `ff_session` cookie to the API.
2. The API's global `AuthGuard` turns the cookie into a user or answers 401. It applies to every route not marked `@Public()`.
3. `WorkspaceGuard` resolves the `:workspaceSlug` route param to a membership, attaches it for `@CurrentWorkspace()`, and enforces `@RequireCapability(...)`.
4. The service queries through Prisma.

Rules that follow from this:

- **Permissions live in one place.** [packages/types/src/roles.ts](packages/types/src/roles.ts) maps each capability to a minimum role. The API enforces it; the web app calls `can()` only to hide controls. A new protected action needs a capability there and `@RequireCapability` on the route.
- **Non-members get a 404, not a 403,** so a workspace's existence is not confirmed. A member whose role is too low gets a 403.
- **Sessions are database rows.** Session and invitation tokens are stored hashed, so a token can be shown only at creation.
- **Sign-in is the one special case in the web app:** the server action reads the session token from the API response and sets it as a cookie on the web app's own origin.

### Web app conventions

- Pages get their session through `requireSession()` or `requireWorkspace(slug)` in [apps/web/src/lib/session.ts](apps/web/src/lib/session.ts).
- Mutations are server actions in `apps/web/src/lib/actions`. They return a `FormState` (`error` or `notice`) for the form, or redirect. Use `messageFrom(error)` for the error text.
- `cacheComponents` is on, so data fetched per request must sit inside a loading boundary. Each new section under `/w/[workspaceSlug]` needs its own `loading.tsx` that re-exports the shared one (`export { default } from "../loading";`). The boundary in the workspace layout does not count when moving between sections.
- `packages/ui` ships TypeScript source with no build step; Next.js compiles it through `transpilePackages`. Colours are CSS variables in `tokens.css`, mapped to Tailwind class names in `tailwind.css`. Adding a colour means editing both.

### Interface design

Read [docs/design.md](docs/design.md) before changing anything a person sees, on the web or, later, in the mobile app. The goal is an interface that is distinctive and plainly functional, and that never looks like a generic AI or SaaS template.

- **Direction: Ink & Signal, sharpened, on glass.** Frosted glass panels (`glass`, `glass-strong`) over an ambient ground (`ground`), one cobalt signal for the next action, a lime highlight only for counts and trend chips, violet only for AI. Interface text is Schibsted Grotesk; anything a business publishes is shown in Newsreader. The lifecycle dot (an empty ring for draft, a filled dot for published) is the signature.
- **Light, dark and system themes.** Every colour is a token with a light and a dark value in `tokens.css`; components never branch on the theme. Check every screen in both themes. Keep the glass fallbacks for reduced transparency and high contrast.
- **Tokens only.** No hex values, pixel font sizes (`text-[13.5px]`) or one-off shadows in components. Use the named type sizes (`text-page`, `text-body`…). A new token goes into `tokens.css`, `tailwind.css` and `theme.ts` together.
- **Build from `packages/ui`.** Add a missing component there instead of styling it inside a page. Complex interactive components come from shadcn (`npx shadcn@latest add <name>` in `packages/ui`) and must be restyled to our tokens before use. Merge classes with `cn`/`cx`, and register any new type size in `packages/ui/src/lib/utils.ts`.
- **Not allowed:** Geist, Inter or Roboto for the interface; all-caps letter-spaced labels; arrows appended to buttons; chips chained with arrows; identical soft-shadow cards for everything; decorative gradients and glows; glass over content the app does not control; emoji icons and sparkles; scroll-in animations on every section. The full list is in docs/design.md.
- **The functional floor:** WCAG 2.2 AA contrast, full keyboard use with visible focus, ARIA Authoring Practices for menus and dialogs, 44 px touch targets, layouts that work from 360 px, a skeleton while loading, a toast after saving, and `ConfirmDialog` (never `window.confirm`) before anything destructive.
- **Check it.** Before calling UI work done, look at it at 390 px and 1440 px in light and dark, and run `npm run test:visual -w @flowforge/web` (it covers both widths and both themes). Use the `frontend-design` skill for new screens when it is available.

### API conventions

- ES modules: relative imports end in `.js`.
- The Prisma client is generated into `apps/api/src/generated` and is not committed. It regenerates on install, build, dev and typecheck.
- `configureApp()` in [apps/api/src/configure-app.ts](apps/api/src/configure-app.ts) sets up cookies, CORS and the validation pipe for both `main.ts` and the e2e tests. Put app-wide setup there so the tests run the same pipeline. The pipe rejects properties a DTO does not declare.
- `packages/types` is compiled to `dist`. The API imports the built output, so Turborepo tasks depend on `^build`. Running an API script on its own after changing types needs `npm run build -w @flowforge/types` first.
- Linting is oxlint, tests are Vitest.

### Environment and tests

- One `.env` at the repository root serves the API and Prisma. Copy `.env.example` to create it. The web app reads `API_URL` and falls back to `http://localhost:4000`.
- End-to-end tests truncate every table before each case. They run against `flowforge_test` (override with `TEST_DATABASE_URL`), never the development database. A new table must be added to the `TRUNCATE` list in [apps/api/test/app.e2e-spec.ts](apps/api/test/app.e2e-spec.ts).
- No mail provider is connected. Invitation links are shown to the inviter in the Team screen and written to the API log.

## Git workflow

Work is tracked in Linear (team `FLO`). For every change:

1. Sync first: `git fetch --all --prune`, then `git rebase origin/main`.
2. Branch name is the Linear issue ID, e.g. `FLO-38`. Create the branch from `origin/main` right after creating the Linear issue (`git switch -c FLO-39 origin/main`), not later.
3. Prefix every commit message with the issue ID, e.g. `FLO-38 generate types on ci/cd`.
4. Write the PR description as a raw Markdown file whose title starts with the issue ID, e.g. `# FLO-38: Generate Next route types before typecheck in CI`. Always also print the full raw Markdown in the chat, in a code block, ready to copy.

If no Linear issue exists for the work, ask before creating a branch.
